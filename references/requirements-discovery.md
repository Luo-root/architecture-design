# 需求澄清与功能拆解

## 进入方式与需求状态

先读取当前请求、已确认讨论、现行文档及相关实现，提取需求来源、时间和适用范围。产品名称只提供讨论入口，不能据此默认业务模式、角色或技术栈；已有系统也不能因有代码就视为需求已经确认。

以本次要设计或修订的范围判断需求状态：

- `CLARIFYING`：仍有会改变功能边界、权限、业务数据、规模或验收的关键问题，需要继续澄清。
- `DESIGNABLE`：影响本次设计的需求已确认；剩余低风险细节有明确假设，可以进入架构设计。
- `BLOCKED`：必要事实暂时无法取得，也不能安全假设；说明影响范围、所需信息和解除条件。

明确的小改动只补受影响的需求，不重新盘问整个产品。关键问题未闭合时，继续整理已知事实、候选功能和不依赖答案的部分；不要把未决部分的模块、数据库或部署方案写成定案。用户明确要求先按假设探索时，可以给条件式候选方案，列清前提及失效后果，不将假设升级为确认事实。

## 最小需求基线

逐条记录 `REQ-*`、内容、来源和状态。事实状态使用 `CONFIRMED`（已确认）、`ASSUMED`（暂定假设）、`OPEN`（待澄清）、`BLOCKED`（暂时无法取得）；需求状态与技术决策状态分别标注所属范围，不能相互替代。

| 类别 | 要弄清的需求事实 | 对后续设计的影响 |
|---|---|---|
| 目标与范围 | 谁遇到什么问题、成功结果、本次必须做/后续做/明确不做 | 决定功能边界和优先级 |
| 角色与权限 | 谁使用、各自能看和操作什么、归属与审批关系 | 决定身份、数据隔离和授权 |
| 业务对象 | 处理什么内容、对象关系、业务上有哪些状态和变化 | 决定领域模型；内部 schema 后续设计 |
| 使用流程 | 触发者、动作、预期结果、异常结果及人工参与点 | 生成功能点及验收场景 |
| 业务规则 | 计价、库存、审批、退款、配额等适用规则及例外 | 约束正确性、一致性与副作用 |
| 规模与质量 | 使用量级、峰值特征、数据增长、时延、可用性和地域要求 | 约束容量、成本与可靠性 |
| 外部边界 | 要连接的系统、已有能力、人工替代、隐私及合规要求 | 约束集成、数据去向和失败处理 |
| 交付约束 | 团队、时间、预算、环境、既有系统、可观察的验收标准 | 判断方案能否实施和交付 |

按实际风险检查这些类别，不要求用户填满一张统一表。`ASSUMED` 写明依据、影响、验证方式与失效后如何调整；业务模式、关键授权、真实支付和数据去向等方向性选择不能自行默认为已确认。技术能力需查文档或实测时记入验证项，不把查证工作转成用户问卷。

功能需求之外保留规模、质量和交付约束；它们可以约束多个功能，不必为了关联 ID 伪造一个用户功能。

## 提问与逐轮收敛

1. 先复述已知目标和当前缺口，复用已有答案；每轮优先选最影响下一步的少量问题，通常 2～4 个。
2. 每个问题只解决一个具体决定，附简短的影响说明，并允许用选项、业务例子或数量级作答；不要直接让用户选缓存、数据库或服务拆分来代替业务澄清。
3. 没有访问量实测时，先问预计多少人使用、是否集中活动、一天约多少订单或任务。可以给有依据的区间假设，后续做容量探针；不强求用户先给精确 QPS、并发或 SLA，也不从日活直接编造峰值保证。
4. 每轮根据答案更新需求事实、功能清单和剩余问题，再决定下一轮。领域细节和少见异常按已经选定的流程继续展开，不一次丢出完整访谈题库。
5. 需要用户选择时，使用当前宿主可用的提问方式等待回答；不把沉默当确认。用户不愿回答时，保留未决项或条件式方案，继续不依赖这些答案的工作。

### 模糊商城需求的提问素材

面对“我要做一个商城软件”，可从下列问题中选本轮最关键的几项，已有答案的直接跳过：

| 问题 | 为什么问 |
|---|---|
| 主要卖哪类商品：实物、数字内容还是服务？给一件典型商品即可。 | 影响库存、履约、交付与售后流程 |
| 有哪些人使用，各自要做什么？例如消费者、运营、商家或经销商。 | 识别真实角色，判断是否涉及多商家隔离与结算；例子不代表都要支持 |
| 首版必须完成哪条购买流程，做到什么结果算交付？ | 明确首版功能和验收，不默认加入促销、分销等能力 |
| 预计多少人使用，会不会有集中抢购或其他访问高峰？大致量级即可。 | 区分常规交易和峰值容量要求，为后续测量建立范围 |

再沿已选流程问支付、扣库存、发货、取消、退款和外部接入等适用规则。问题顺序由本次缺口决定，商城问题不能直接套给桌面工具、内容平台或内部系统。

## 边澄清边拆功能

澄清过程中就建立初版功能清单，用答案增量修订，不要求先完成架构契约才能列功能：

```text
角色/系统 → 想完成的事 → 业务对象 → 操作 → 可观察结果 → 规则与验收
```

每个 `F-*` 记录关联 `REQ-*`、使用者、目标、输入与业务对象、正常/异常结果、首版或后续范围，以及已确认/候选/排除状态。功能按完整业务动作拆分，例如提交订单、处理退款；不直接等同于页面、按钮、数据库表或微服务。

- 用角色和流程交叉检查遗漏；需求支持多角色时，分别检查其业务动作，不用“用户管理”一项掩盖全部角色的独立能力。
- 检查适用的权限、设置、导入导出、升级、删除、恢复、诊断和审计；需要提供的进入范围，明确不提供的写原因，不自动把检查清单扩成产品功能。
- 产品侧先弄清失败时希望看到什么、谁可处理和哪些结果不能丢。状态机、事务、幂等键、内部恢复机制和完整八项契约在后续设计阶段闭合，不要求用户预先给技术答案。
- 非功能约束单列，并关联它影响的功能、技术决策和验收。派生的必要功能标明推导依据；会扩大业务范围的保留为候选，不自行提升为用户要求。
- 覆盖关系是 `REQ-* → 功能/横切约束 → 八项契约 → DEC-* → 验收/反例`；需求阶段允许后续列为空并注明阶段，不伪装已完成设计。

## 跨轮更新编号账本

一旦分配需求或功能 ID，后续以账本增量更新，不按本轮叙述顺序重新编清单。账本的最小列为：`ID | 首次定义的事项 | 当前范围/状态 | 关联需求或承接ID`。同一事项的细化写在当前范围，不新建平行条目；表格行可以重排，ID 与首次定义的事项不能重绑。

每轮在写新方案前依次执行：

1. 从上一份账本或已有对话恢复所有已分配 ID 及原义，包括退役项，分别记录各前缀已用编号。没有可恢复基线时，说明缺失并补取材料，不凭记忆猜旧号。
2. 将本轮信息逐项归为细化已有、真正新增、拆分、合并或退役。已有事项沿用原 ID；新增事项使用该前缀尚未使用的编号，不填退役号，也不因进入架构阶段重新从 1 编号。
3. 拆分时保留旧项，列出旧项到各子项的对应范围；合并时保留各旧项到承接项的映射。映射后说明谁负责当前行为，旧项作为历史或聚合入口，不留下两套重叠的执行责任。仅调整当前范围或细化约束不需要另发 ID。
4. 更新同一份账本及其契约、决策、验收引用，再从账本生成答复。答复可只显示变化项，并注明未变项沿用哪一基线；退役项保留原义及退役理由，不从历史中消失。对话内用简表即可，只有任务要求落文档时才写入对应设计材料。

交付前把新账本与旧账本逐项对照：旧 ID 是否都有当前落点；同一 ID 是否仍指原事项；新增 ID 是否未用；拆分合并是否有完整映射；引用是否存在且没有失效或重复责任。发现冲突先修账本与引用，再输出方案。已经发出过错误编号时，按各编号最早的有效定义逐项消歧，列出错误用法到正确条目的对应关系；不能只修被点名的两项而漏掉同轮其他旧号。

例如原 `F-07` 是“导出文档”，后来增加“预览导出内容”，导出仍为 `F-07`，预览分配新 ID；取消导出时将 `F-07` 标为退役，不能将它改指预览。判断依据是业务事项与责任，不能只靠名称相似或 ID 数量相等。

## 何时可以进入架构设计

对本次拟定案的范围确认：目标与范围、相关角色及授权、主要业务对象、主流程的正常/异常结果和验收、影响正确性的业务规则、规模与质量目标、外部及交付约束。无适用要求的类别说明原因；低风险未知项有可追踪假设。

达到这些条件即可标为 `DESIGNABLE` 并进入功能契约和技术决策，不必等全部产品细节确定。需求与设计可以迭代；某个未决分支不阻塞已经明确且不依赖它的部分。仍在 `CLARIFYING` 或 `BLOCKED` 的部分交付已知事实、候选功能、问题、假设和进入设计的条件，不能声称其架构已收敛。

## 需求改变后的处理

用户修改定位、角色、范围、规模或业务规则时：

- 记录新决定及其替代的旧要求，明确新旧基线；来源冲突时优先识别最新的用户决定，不能用旧文档或原型覆盖它。
- 沿 `REQ-* → F-* / 横切约束 → 契约 → DEC-* → 验收` 列出保留、调整、移出本次范围或待重审项。稳定 ID 保留替代关系，不静默抹掉历史依据。
- 重新判断受影响范围的需求状态，只补新增缺口；将不再成立的架构决定标为待重审，检查实现、迁移和恢复的受影响位置。
- 调整设计范围不自动授权删除既有实现或数据；具体修改遵循当前任务授权。

## 按阶段交付

需求澄清阶段交付需求摘要、当前范围和状态、已有答案、候选功能、暂定假设、本轮问题与下一步条件；可用一张简表表达，小任务不强制完整文档。

进入设计后沿用相同需求与功能 ID，补责任、接口、数据、状态和失败机制，以及决策和验收位置。未进入本次范围和仍缺证据的部分保持可见。
